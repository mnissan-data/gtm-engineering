The Unofficial Field Guide to Claude Code and Cowork

A mental model for people who are already using these tools and want the pieces to click.

By Michael Nissan

Last updated: April 22, 2026 Unofficial, not Anthropic documentation ~45 pages equivalent

A personal note from the author. After using Claude Code for the last three months, I had a lot of questions about certain features and how they work, what does this thing actually do, when do I reach for it, how does it fit with everything else? I put this together to answer those questions for myself. If you're using Claude Code (or Cowork) for your own projects, maybe it'll help you too.

There's a lot of great official documentation on Anthropic's site, and you should read it. I built this in addition to that, not instead of it. I'm a visual learner. I need charts, diagrams, and side-by-side comparisons to make these concepts stick. If that's you too, this guide is for you.

TL;DR

  1. Claude Code and Cowork share one brain, an LLM in a loop with tools. They differ in surface: Claude Code is for code in a terminal or IDE; Cowork is a desktop app for anyone with files and tasks.
  2. Four things shape what Claude does for you, in order of leverage: the model, the context window, your project setup (CLAUDE.md, skills, MCPs), and your prompt. Most people obsess over the prompt. The leverage is further up the stack.
  3. A skill gives Claude judgment; an MCP gives Claude capability. You often want both. MCP schemas load at session start, connecting a chatty MCP costs tokens before you type a word.
  4. Plan mode is read-only, not "no tools." It can run shell commands to explore, just can't mutate. Common misconception.
  5. "Agent" means four different things in this ecosystem. Conflating them causes most of the confusion.
  6. The terminal is still the most feature-complete Claude Code surface, though the VS Code extension and desktop app are catching up. Verify for your version.
  7. Investing in CLAUDE.md + a few good skills beats writing longer prompts, every time. Prompts are turn-by-turn; setup is every turn forever.

How to read this guide

Every concept gets the same treatment: plain-English explanation → one concrete example → a best-practice callout. Recurring Common confusions boxes flag the misconceptions I've tripped on.

Skip around. The parts are mostly independent. If you've never thought hard about what a token is, start at Part 0. If you already have the foundations, jump to Part 2.

Part 0Foundations

If you've been using Claude Code for months but nobody ever sat you down and explained what an LLM actually is, this part is for you. It's short. It unlocks the rest.

What an LLM actually is

A Large Language Model is a pattern-matcher on text. You feed it a sequence of text; it predicts what text would most plausibly come next.

It is not a database (it doesn't "look things up"). It is not a brain (no memory between conversations unless you give it one). It is not a search engine (though it can be wired to one). It's more like an extremely well-read improv partner: you set the scene, it continues the scene, one word at a time.

Everything else, agents, tools, skills, MCPs, is scaffolding around that core trick.

Why this matters

When Claude gets something wrong, the question isn't "why is it broken?" It's "what pattern did I give it that led to this continuation?" That reframe changes how you debug.

What a token is

Tokens are the units the model actually reads and writes. Not characters, not words, somewhere in between. Roughly:

  • "hello" → 1 token
  • "unbelievable" → 3 tokens (un, believ, able)
  • "🦙" → several tokens (emoji are expensive)
  • Typical English prose → ~0.75 tokens per word, or ~4 characters per token

You pay for tokens in two places: input (what you send the model) and output (what it generates). Input is cheaper per token but there's way more of it, so it dominates cost on long sessions.

Common confusion

People think "short prompts are cheap." They are, but the prompt is a tiny fraction of what's actually in context. Every file Claude read, every tool result, every skill description loaded at session start is also input tokens. The prompt is the tip of the iceberg.

What a context window is

The context window is everything the model can see at once when deciding what to say next. It's finite. Claude models currently offer up to a 1M-token context window in Claude Code, which is huge, but not infinite, and not free.

Think of it as RAM, not a hard drive. Anything not in the context window might as well not exist, as far as this particular response is concerned. And once something enters the window, it stays there until you explicitly clear it or it gets compacted away.

Why "models forget"

They don't, really. Either (a) the info was never in the window, (b) it was evicted by compaction, or (c) it's still there but buried so deep the model's attention dilutes across it. All three feel like "forgetting" from the outside.

What an agent is

An agent is an LLM in a loop that can take actions in the world via tools.

That's it. That's the whole thing. Claude Code, Cowork, Cursor's agent mode, Windsurf's Cascade, Antigravity, the SDK, they're all variations on this loop. What differs is which tools are available, how results come back, and what wraps around it.

Best practice

The unit of an agent is not "the response." It's a whole loop of thinking and acting until it decides it's done. That's why you sometimes see Claude make 15 tool calls for one of your messages. One turn, many actions.

Why prompts matter; why context matters more

A great prompt on a blank context is a smart stranger with no files. A mediocre prompt on well-curated context, your CLAUDE.md, the right skills loaded, your codebase already referenced, is a seasoned teammate who just needs a nudge.

Invest in the context. Prompts are disposable. Context setup compounds.

All the pieces in motion: one paragraph

You open Claude Code in your project. It reads your CLAUDE.md (context). You type "fix the failing auth test" (prompt). The model, seeing CLAUDE.md says pnpm test runs tests, decides to call the Bash tool (agent loop, tool call). The test output returns as a tool result (into context). The model reads the stack trace, opens the relevant file with Read (another tool call), sees the bug, calls Edit to patch it, calls Bash again to re-run the test, sees it pass, and answers: "Fixed. The test was asserting on the old error message, updated it." That whole sequence was one turn. It used maybe 12,000 tokens. You typed 6 words. That's the game.

Part 1Orientation: what am I actually using?

Claude Code vs Claude Cowork

Both are the same agent loop. They differ in surface, audience, and defaults.

Claude Code is a developer tool. Primarily a CLI in your terminal, inside your project folder. Deep file-system access, shell, git integration. What you use to build software.

Cowork is a desktop app for anyone who works with files and tasks, not just developers. Workspace folder, connectors to Gmail / Calendar / Drive / Linear / Slack, scheduled tasks, artifacts (interactive HTML views that persist between sessions). Point a PM, designer, marketer, or ops person at Cowork.

Under the hood: same loop, same models, mostly same tools. Different wrappers.

Important caveat about "the IDE"

When you're using an IDE, there are two ways to run Claude Code in there, and people conflate them:

  1. The Claude Code extension, installed from the marketplace, lives in a side panel, sees your open files, shows inline diffs.
  2. Claude Code in the IDE's integrated terminal, same claude binary you'd run anywhere else, just inside your editor's terminal pane. Identical to running it in your OS terminal.

You can also run the standalone OS terminal next to your IDE, that's effectively the same as #2. So when you hear "I use Claude Code in VS Code," ask which one. They behave differently and have different feature parity.

Verify for your version

This landscape shifts every month or two. The "terminal is most feature-complete" framing has been directionally true for a while, but specific features land on specific surfaces in different orders. Always check the current release notes.

IDE primer (for non-developers, and developers who've only used one)

An IDE (Integrated Development Environment) is a text editor with superpowers for writing code: syntax highlighting, autocomplete, inline errors, debugging, file navigation, git integration. VS Code is the dominant one. Cursor, Windsurf, and Google's Antigravity are AI-first IDEs, all are VS Code forks (or close cousins) with AI pushed to the center of the UX.

Honest differences as of April 2026:

Framework for choosing

If you're picking for personal use and already use Claude heavily: VS Code + Claude Code extension is the lowest-friction choice. If you're joining a company, you'll likely inherit whatever they use, don't fight it. The differences between these tools are smaller than the differences between "well-set-up project" and "not-set-up project."

Mobile

Cowork has a proper mobile experience. Claude Code on mobile is about monitoring and light interaction with remote sessions, not full terminal work. Mobile push notifications on Claude Code landed in early 2026, you'll get pinged when a long task needs input or finishes.

Personal use vs company use

The big difference: at a company, your CLAUDE.md, skills, and .mcp.json are shared with teammates via git. Your working patterns become part of the repo. For personal projects, you can be messier, but investing in the setup still pays off, because future-you is also a teammate.

Mobile rule of thumb

Use mobile Cowork for thinking, monitoring, and capturing. Use desktop Cowork or Claude Code for making. Mobile is great for "what should I cover in my 1:1?" or "summarize what landed in my inbox." It's not great for "make me a 30-slide pitch deck."

Using Claude Code and Cowork together, a combined workflow

You don't have to pick one. The most natural pattern I've found: Cowork to think and design, Claude Code to build. Here's a worked example, building a simple internal tool from scratch.

Step-by-step, the workflow looks like:

  1. Brainstorm in mobile Cowork. "I want a tool that lets ops people see open Linear issues by team." Voice it in, get a back-and-forth.
  2. Spec in desktop Cowork. Ask Cowork to turn the brainstorm into a clean spec.md. Save it to your workspace folder.
  3. Build a clickable artifact. Have Cowork generate a live HTML mockup as an artifact, pulling sample data from the Linear connector. Review it with the people who'll actually use it.
  4. Hand off to Claude Code. In your IDE, create the repo. Drop the spec.md in docs/. Reference it from CLAUDE.md with @docs/spec.md. Now Claude Code starts every turn knowing exactly what you're building.
  5. Implement. Use Plan mode for the first pass, then Accept Edits to grind through. Tests, types, commits.
  6. Monitor on mobile. When a build or test run takes a while, Cowork mobile pings you when it needs input, push notifications on a background Claude Code session.
The pattern

Cowork is for the parts where you're figuring out what to make; Claude Code is for the parts where you're making it. Both can do both, but each is much better at its half.

Pairing an IDE project with a Cowork project (and how they "talk")

The honest answer in April 2026: they don't share state directly. Claude Code lives in your repo; Cowork lives in your workspace folder and the cloud. There's no automatic two-way sync of conversation history, no shared "memory" between sessions. But there are several practical ways to keep them paired:

Three patterns for keeping context in sync

PatternHow it worksBest for
Shared folderPoint Cowork's workspace folder at your repo (or a sibling folder). Both tools read/write the same files, spec.md, decisions.md, generated docs.Solo work. Simplest path. The filesystem is the integration.
Shared CLAUDE.md / memory filesClaude Code reads CLAUDE.md from the repo. Cowork can read the same file via its workspace folder. One source of truth for "what does the model need to know about this project?"Teams. Anyone on the project gets the same context whichever tool they open.

Migrating context between them

When you've done a big chunk of work in one and want to continue in the other, the move is usually: have the source surface write a handoff doc, then point the destination surface at it.

  • Cowork → Claude Code. "Summarize what we decided in this conversation as handoff.md, with: the goal, key decisions, open questions, and the next three steps." Save to the repo. In Claude Code, start with: "Read handoff.md, then begin step 1."
  • Claude Code → Cowork. Have Claude Code write a status update to status.md at the end of a long session, what shipped, what's blocked, what's next. Open Cowork on top of the same folder; ask it to draft the Slack/email update from status.md.
Common confusion

"Why doesn't my Cowork conversation show up in Claude Code?" Because they don't share a conversation log. Treat the filesystem as the integration point, not the chat history. Anything you want both to see, write to a file both can read.

Pattern that scales

For any project I expect to use both tools on, I create three files in the repo: spec.md (what we're building), decisions.md (append-only log of choices), and handoff.md (current state, refreshed at each switch). Both tools read and write these. They're the shared brain.

Decision tree

Are you writing code?
├─ Yes → Claude Code (terminal if power-user, VS Code extension otherwise)
└─ No
   ├─ Files, docs, email, tasks? → Cowork
   ├─ Quick one-off question? → claude.ai or the desktop app
   └─ Building an agent into your own product? → Claude Agent SDK

Part 2Anatomy of a Claude Code project

This is the part most people never get a clean mental model of. Four building blocks: CLAUDE.md, skills, MCPs, sub-agents. They compose.

CLAUDE.md

CLAUDE.md is a system-prompt append, not a README. Every turn, its content is silently prepended to Claude's context. It's how you teach Claude the durable, project-specific truths: "we use pnpm, not npm." "Tests live in __tests__/, run with pnpm test." "Don't touch legacy/ without asking."

Key properties:

  • Loaded every turn. Every single message, the whole file's tokens are paid. Keep it tight.
  • Imports via @path. Write @docs/architecture.md in your CLAUDE.md and Claude Code inlines that file. Lets you split a big brain into smaller files.
  • CLAUDE.local.md for machine-specific stuff. Personal notes, paths, toggles you don't want in git. Gitignored by convention.
  • Conciseness rules. Write it like a sharp team onboarding doc, not a textbook. Short sections. Bullet points. Zero filler. If a line doesn't change what Claude does, delete it.
Common confusion

CLAUDE.md is not a README. READMEs describe a project to humans. CLAUDE.md tells Claude how to work inside the project. Different audience, different content.

Rule of thumb

If you're writing the same instructions into prompts over and over, move them to CLAUDE.md. If you're writing them into CLAUDE.md and only one person on your team uses them, move them to CLAUDE.local.md.

Skills

A skill is a folder with a SKILL.md and optionally scripts/reference files. It teaches Claude how to do one specific kind of task when it becomes relevant, without paying for all that context every single turn.

.claude/skills/pptx/
├── SKILL.md          # frontmatter + instructions
├── scripts/
│   └── build_deck.py
└── reference/
    └── slide_templates.md

Naming a skill: folder, file, frontmatter

A skill has three names that need to agree, plus one rule per layer:

Naming heuristics

Verb-first for skills that do something (draft-outreach, build-dashboard). Noun-only for format-skills that wrap a file type (pptx, docx, pdf). Avoid generic names like helper, utils, writer, they collide with other plugins and they don't tell future-you what they do.

Why .md and not some other format?

The whole skill folder is conventionally Markdown plus optional scripts. Three reasons it's .md specifically, not .txt, .yaml, .json, or a custom format:

  1. The model already speaks Markdown fluently. Claude was trained on enormous amounts of Markdown. READMEs, docs, blog posts. Headers, lists, code fences, tables: zero translation cost. JSON or YAML would be a worse signal.
  2. Humans read and edit it directly. A skill should be reviewable in ten seconds. Markdown gives you human and machine readability with no toolchain.
  3. YAML frontmatter handles the structured bits. Skills need some structured metadata (name, description, optional allowed-tools). YAML at the top of an .md file is the standard way to do that, same pattern as Jekyll, Hugo, and a thousand static-site generators.
  4. It composes with imports. CLAUDE.md uses @path imports; reference files inside skills are also Markdown; everything stitches together without format conversion.

The minimal SKILL.md looks like this:

---
name: release-notes-writer
description: Use when the user asks to draft release notes from git
  commits. Triggers on "release notes", "changelog", or "what shipped
  in vX.Y". Do NOT use for marketing announcements or blog posts.
---

# Release notes writer

Read the last N commits with `git log --since=...`, group into
User-facing / Bug fixes / Performance / Internal, and write in
second person, past tense, no emoji. Always include "Thanks to" with
unique commit authors.
Don't reach for non-Markdown formats

You'll occasionally see proposals to use JSON or YAML files for skill instructions. Resist. The instructions are prose Claude will read and follow. Markdown wins. Reserve YAML for the frontmatter, JSON for genuine config files (e.g. .mcp.json).

Progressive disclosure, the key insight

Only the skill's name and description are loaded at session start. The body, instructions, reference files, scripts, is only pulled into context if the description matches what the user asks. This is why skills scale. You can have hundreds installed and pay almost nothing for the ones that don't fire.

The description is the trigger

Claude decides whether to invoke a skill based on its description. This is where most skill failures happen.

Bad description: "Helpful for presentations." (Too vague. What counts? When?)

Good description: "Use when the user wants to create, read, edit, or manipulate PowerPoint (.pptx) files, or asks for a slide deck, presentation, or pitch deck. Do NOT use for Google Slides or PDFs."

The good version has explicit triggers (verbs + file types), concrete synonyms, and exclusions. Write descriptions as if a co-worker is deciding whether to interrupt you for this task.

Skill categories

  • Project/domain skills. "How we write RFCs at Acme." Lives in the repo.
  • Task skills. docx, pptx, xlsx, pdf. Generic output creation. Pull from trusted sources.
  • Tool-wrapper skills. Judgment on top of an MCP. "When querying the warehouse via the MCP, always filter by env='prod' first."
MCP + skill together

MCP = capability ("can call the warehouse"). Skill = judgment ("here's how we call the warehouse"). You almost always want both for an external tool that matters to your workflow.

Where your skills come from

  1. Build from scratch when the need is company-specific or deeply personal to your workflow.
  2. Pull from someone else's plugin or GitHub repo when the need is generic. docx, pptx, pdf, popular-framework helpers. Don't rebuild what good versions already exist for.
  3. Fork and customize when something is close but not quite.

Trust review, same as for MCPs, before installing any skill from outside: check the source, the maintainer, what the skill's scripts actually do. Skills can execute code.

  • 🟢 Green: Anthropic-official, reputable maintainer, simple readable scripts, no network, no secret handling.
  • 🟡 Yellow: Active community maintainer, moderate complexity, you've read the scripts.
  • 🔴 Red: Unknown author, complex scripts, network calls, secret prompts. Don't install.

Debugging: "why didn't my skill fire?"

  • Is the description specific enough? (Test: paste your user message + description into a chat and ask "would this skill fire?")
  • Does Claude know the skill exists? (Check /doctor or equivalent.)
  • Is the user's phrasing too different from the description's keywords?
  • Is a different skill with a broader description winning?
  • Is your skill file actually being discovered (correct folder, correct frontmatter)?

MCPs (Model Context Protocol)

An MCP server is a standard way to expose external tools (APIs, databases, services) to an LLM agent. MCP is now an open standard, donated by Anthropic to the Agentic AI Foundation (under the Linux Foundation). Any LLM that speaks MCP can use any MCP server.

How MCPs differ from skills

  • A skill is prose + optional scripts, scoped to your project or install.
  • An MCP is a running process (or remote service) that exposes tools Claude can call with typed parameters.

A skill instructs Claude. An MCP gives Claude new tools.

Install scope

User-level (~/.claude/ or claude mcp add ...), available in every project. Project-level (.mcp.json at project root), shared with your team via git.

Example, add an MCP at user scope:

claude mcp add linear --scope user \
  --command "npx -y @linear/mcp-server" \
  --env LINEAR_API_KEY=sk-...

Example .mcp.json at project scope:

{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/app"]
    }
  }
}

Personal things (your API keys, your scratchpad) → user scope. Shared things the whole team needs → project scope.

Schema-loading reality, the expensive part

The hidden cost

Every connected MCP loads all its tool schemas into context at session start. That's the full JSONSchema for every tool the MCP exposes, names, descriptions, parameters, types. Before you type a word, you're paying for every tool in every connected MCP.

A chatty MCP with 40 tools can easily consume 5-10k tokens just in schemas. Multiply by every session. This is the single biggest invisible cost in a Claude Code project.

The newer Tool Search feature (recently released for the API) flips this: only tool names load at start; full schemas are fetched on demand. Worth enabling where available.

Trust and safety

MCPs are programs running on your machine (or remote services handed your credentials). Treat installing an MCP like running curl | bash. Before adding one: who's the maintainer, is the source repo active, what permissions does it request, how does it handle secrets? Red/yellow/green applies here too.

Official vs community

Anthropic publishes an official MCP directory with 75+ connectors covering the usual: Gmail, Drive, Linear, Notion, Jira, Slack, GitHub, Figma. Start there. The community ecosystem is enormous but variable quality.

When to build your own MCP

  • You have a proprietary internal system you want Claude to reach.
  • Existing MCPs are close but missing a tool you need constantly.
  • You want the same capability shared across your team.

Skip building one when a skill that shells out to your CLI would do the same job with less infrastructure.

Do I need a skill on top of my MCP?

Usually yes, if the MCP matters to your workflow. Worked examples:

  • Warehouse (Snowflake/BigQuery). MCP gives Claude the ability to query. A skill tells it: which schemas you use, naming conventions, common joins, the one metric definition that causes 80% of disputes, when to stop and ask before a long query.
  • Clay. MCP reads/writes workbooks and enrichment tables. A skill encodes your ICP definition, trusted enrichment sources, and what good output looks like.
  • Figma. MCP exposes files, pages, nodes. A skill encodes your design system tokens and what "handoff-ready" means at your company.

Sub-agents (and the four meanings of "agent")

The word "agent" in this ecosystem means at least four distinct things. Conflating them is a major source of confusion.

  1. The Task tool. Claude Code's built-in general-purpose sub-agent spawner. You say "explore how auth is wired across the codebase and summarize." It launches a sub-agent; the sub-agent does its own multi-tool exploration; returns a single summary message.
  2. Named sub-agents in .claude/agents/. Specialized sub-agents with their own system prompt, tool allowlist, and model. Example: a code-reviewer agent that only gets read-only tools.
  3. Multiple Task calls in one message. Fire several Task calls at once; they run in parallel, all report back to the same parent. Good for "look at these five things concurrently."
  4. Multiple Claude Code sessions. Open two terminals, run Claude Code in each. They don't share context. They don't coordinate. Just two humans' worth of Claude side-by-side.

Why sub-agents have isolated context windows

This is the whole point. A sub-agent's exploration, all the files it reads, tool outputs, reasoning, happens in its own context window. When it's done, it returns only its final message to the parent. The parent context stays clean.

The cost: the return message costs parent tokens. And the sub-agent itself costs tokens, just in its own window. You didn't get the work free, you paid the tokens in a different bucket, and kept the main bucket clean.

Common confusion

"Sub-agents are faster." Not inherently. They're the same model, same loop. They're isolating, not accelerating. Parallel Task calls are faster for independent work because they run concurrently.

Part 4Modes: how you drive the agent

Modes control what Claude is allowed to do without asking you. They're about permission, not capability.

The four modes (plus the new fifth)

  • Default. Claude asks for permission before any tool that writes, edits, or executes. You approve or deny each one. Most conservative.
  • Accept Edits. Auto-approves file edits and common filesystem Bash (mkdir, touch, rm, mv, cp, sed). Review via git diff after the fact.
  • Plan. Claude researches and proposes, reads files, runs read-only shell commands, writes a plan, but does not edit. Read-only, not no-tools.
  • Bypass Permissions. All permission checks off. Every tool call runs immediately. Only use in disposable sandboxes. Invoked with the --dangerously-skip-permissions flag.
  • Auto mode (released March 2026). A safer alternative to Bypass. A Sonnet-4.6 classifier evaluates each tool call for risk, auto-approves safe ones, blocks or prompts on dangerous ones (mass delete, data exfil, weird network calls).
Common confusion

Plan mode is often described as "it can't do anything." Wrong, it can read files, list directories, run read-only shell commands, do web searches. What it can't do is mutate (Edit, Write, destructive Bash). Perfect for "figure out how this works before touching it."

Shift+Tab cycling

In the terminal, Shift+Tab cycles through: normal → auto-accept edits → plan → normal. Auto mode and Bypass are invoked separately. You flip mid-session freely.

Allow / deny lists in settings.json

Beyond modes, you can permanently allow or deny specific tool patterns in .claude/settings.json (project) or ~/.claude/settings.json (user):

{
  "permissions": {
    "allow": ["Bash(pnpm test*)", "Bash(pnpm lint*)", "Read(*)"],
    "deny": ["Bash(rm -rf *)", "Bash(git push*)"]
  }
}

Use this to pre-approve the boring stuff (tests, lints, typechecks) so you're not tab-tab-tab'ing through them all day, and to hard-block the things you never want Claude to do unprompted.

Part 5Plugins, connectors, and how it all fits

Plugin anatomy

A plugin is a bundle. It can contain: skills (0..n), sub-agents (0..n), MCP server definitions (0..n, pre-configured), slash commands (0..n), hooks (0..n). One install gives you all of them.

Example: a python-development plugin might ship 16 skills, 3 sub-agents, and a linting hook, available with one /plugin install command.

Anthropic-approved plugins: trust signals

  • Published by Anthropic or a known integration partner.
  • Source code on GitHub, recent commits, issues being answered.
  • Clear documentation about what it reads/writes and what permissions it needs.
  • No post-install steps that download opaque binaries.

Quality in community marketplaces varies wildly. Apply the same red/yellow/green check you'd use for a random npm package.

Plugin vs connector vs skill

These three get muddled, especially in Cowork conversations.

  • Skill: instructions + optional scripts. Teaches Claude how to do a thing.
  • MCP server: a process exposing tools. Gives Claude the ability to do a thing.
  • Connector: Cowork's user-facing name for an MCP-backed integration to a specific service. You "connect" your account; under the hood it's an MCP.
  • Plugin: a package bundling any combination of skills, MCP servers, agents, hooks, commands.

Feature matrix: MCPs vs connectors vs plugins

If you squint, these three overlap. The matrix below spells out what each one actually does, so you can pick the right one without guessing. A connector is an MCP with OAuth and a friendly UI; a plugin is a bundle that may or may not include an MCP, plus other things an MCP can't carry on its own.

Part 6Hooks

Hooks are shell commands that fire at specific points in Claude Code's lifecycle. They're how you make behavior deterministic, force formatting, block dangerous commands, inject context, log activity, send notifications.

Exit-code semantics

  • Exit 0: allow, carry on. Stdout can be added to context where supported.
  • Exit 2: block. On PreToolUse, blocks the tool. On UserPromptSubmit, blocks the message.
  • Other non-zero: error, logged; Claude continues.

Three killer examples

1. Auto-format on save

// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{"type": "command", "command": "prettier --write $CLAUDE_TOOL_INPUT_FILE_PATH"}]
    }]
  }
}

2. Block dangerous SQL in a data project

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{"type": "command", "command": "scripts/sql-safety.sh"}]
    }]
  }
}

Where sql-safety.sh inspects the command and exits 2 if it sees DROP|DELETE|UPDATE outside allowlisted scratch schemas.

3. Re-inject critical context on compaction

{
  "hooks": {
    "PreCompact": [{
      "hooks": [{"type": "command", "command": "cat docs/invariants.md"}]
    }]
  }
}

Whatever the hook prints to stdout is added back into context, so your project invariants survive compaction.

Security

Hooks run with your shell privileges. A compromised or malicious hook can do anything you can do from the terminal: delete files, send secrets, install software. Review every hook you install. Pin versions. Don't pull hook scripts from random gists.

Part 7The Claude Agent SDK

The Claude Agent SDK is Anthropic's framework for building your own agents on top of the same loop Claude Code uses. The SDK was effectively extracted from Claude Code's internals, they share the agent loop, tool-use semantics, MCP support. Claude Code is, in a sense, one application built on the SDK; you can build others.

When to reach for the SDK

  • You want to build a custom agent and ship it to users (your own product, an internal tool).
  • You want an agent running as a scheduled job or service, not a human-driven session.
  • You want to build an MCP server, the SDK tooling makes this straightforward.
  • You want the Claude Code experience embedded in your own app.

If you just want to use Claude to do work for yourself, you don't need the SDK. Claude Code and Cowork already wrap it.

Minimal example (conceptual)

from anthropic.agent import Agent

agent = Agent(
    system="You are a release-notes writer. ...",
    tools=[read_commits_tool, write_file_tool],
)
result = agent.run("Draft release notes for v1.4 from the last 20 commits.")
print(result.messages[-1].content)

Under the hood: same loop as Claude Code. Prompt → think → tool → result → repeat.

Connection to MCP

An MCP server is, in practice, a small program that exposes typed tools. The SDK ships helpers for building and hosting one. Most "we connected a new internal system to Claude" stories at companies end up being: write an MCP server with the SDK, deploy it, add it to .mcp.json.

Part 8Tokens and context, in depth

Everything in this part boils down to: tokens are scarce; plan accordingly.

The counterintuitive rule

Once something enters context, it stays until you /compact or /clear. There is no automatic cleanup of the 3,000-line log file you told Claude to read in turn 4. It's still there in turn 40. This is why long sessions gradually slow down and lose focus.

When tokens are spent

CostWhen
System promptEvery turn
CLAUDE.md + importsEvery turn
Skill descriptionsEvery turn
Skill bodiesOnly when invoked
MCP tool schemasAt session start (until Tool Search)
MCP tool resultsWhen tools are called
Files readWhen read
Sub-agent return messagesWhen a sub-agent finishes
Conversation historyEvery turn, cumulatively

Degradation signals

Signs your context is overloaded:

  • Claude starts re-reading files it already read.
  • It contradicts something it knew earlier in the session.
  • Responses get repetitive or hedgy.
  • Tool calls become unfocused.
  • Simple tasks take surprisingly long.

When you see these: /compact, /clear, or start a new session.

/clear vs /compact vs new session

  • /clear, wipe the conversation, keep the project setup. Fast reset.
  • /compact, summarize older turns into a brief, keep the summary, discard originals. Use when there's valuable context buried in a long session.
  • New session, full restart. Use when starting a genuinely new task.

Heuristic thresholds (rules of thumb, not official)

  • ~60% used → soft warning. Is everything in context still relevant?
  • ~80% used → hard warning. Compact or clear before the next big task.
  • >90% used → you're probably getting degraded output and paying the most per turn.
Common confusion

These aren't Anthropic-published numbers. They're heuristics that match how most people experience the quality curve. Your mileage will vary by model and task.

Prompt caching basics

Anthropic's API supports prompt caching: stable prefixes (system prompt, CLAUDE.md, large reference docs) can be cached server-side so subsequent turns pay a small fraction of the token cost. Claude Code uses this automatically where it can. Implication for you: put stable context at the top (which CLAUDE.md naturally does) and avoid gratuitously editing it mid-session.

Part 9Prompts vs project setup (demonstrated tradeoff)

Same task, two setups. Watch the tokens and the quality.

The task

Write release notes for the v1.4 release based on recent git commits.

Setup A: bare CLAUDE.md, detailed prompt

CLAUDE.md is one line:

This is a web app.

Prompt:

Write release notes for v1.4. Get the commits from the last two weeks using
`git log --since=2.weeks` and group them into: User-facing features,
Bug fixes, Performance, and Internal/Chore. Write in the second person,
upbeat but not breathless. Include a 'Thanks to' section listing unique
contributors from the commits. Output as markdown suitable for our
changelog page. Audience is end users, not engineers. Skip dependency
bumps unless they're user-visible. Use past tense verbs. No emojis.

Tokens spent (rough): ~200 prompt + ~8,000 over the turn. Output quality: pretty good, you specified everything.

Setup B: rich CLAUDE.md, terse prompt

CLAUDE.md:

# Project
Web app. Release notes live in `CHANGELOG.md`.

## Release notes style
- Audience: end users.
- Second person, upbeat, not breathless, past tense, no emojis.
- Group commits into: User-facing features, Bug fixes, Performance, Internal.
- Skip dependency bumps unless user-visible.
- 'Thanks to' section listing unique contributors.
- Use `git log --since=2.weeks` to gather commits.

Prompt:

Release notes for v1.4.

Tokens spent (rough): ~50 prompt + the same ~8,000 over the turn. But also ~200 extra tokens in CLAUDE.md every turn of this session, not just this one.

Output quality: identical. And next week, when you ask for v1.5, you type four words.

Heuristics

  • One-off, new territory? Put it in the prompt. Don't pollute CLAUDE.md with single-use stuff.
  • You've written this twice? Move it to CLAUDE.md (or a skill).
  • It's a reusable workflow? Consider a skill, body loads only when relevant.
  • General capability tied to an external system? MCP.
Rule of three

The third time you write the same context into a prompt, you've earned the right (obligation) to move it up the stack.

Part 10Cowork-specific mental model

Cowork shares the engine. It differs in surface and in a handful of concepts that don't exist in Claude Code.

How Cowork differs

  • Audience. Not engineer-primary. A PM, designer, marketer, or ops person can use it without ever touching a terminal.
  • Surface. Desktop app + mobile. No terminal, no direct CLI. File tools and a sandboxed shell, wrapped in a chat-like UI.
  • Connectors first. Cowork leans on MCP connectors (Gmail, Calendar, Drive, Linear, Notion, Slack, Salesforce, Clay, and the rest) as the primary way to reach your data.
  • Plugins. Same mechanism as Claude Code; Cowork surfaces them differently (a plugin registry inside the app).

Artifacts vs files

  • File. Lives in a folder. Regular file. Static.
  • Artifact. A live HTML view that opens in the Cowork sidebar, persists across sessions, and can re-fetch data from your connectors each time you open it. Think "a dashboard or tracker you'll come back to," not "a one-off explainer."
Rule

If the user will look at it again and the underlying data changes, artifact. If it's a static deliverable, file.

Uploads, outputs, workspace folder

  • Uploads. Files you attach to a message. Read-only; Claude can examine them.
  • Outputs. The temporary scratchpad Claude writes to during a session. Users don't see these directly.
  • Workspace folder. A real folder on your computer that you select. This is where final deliverables go so you can actually use them.

Scheduled tasks

Cowork supports running a prompt on a schedule, daily morning brief, weekly digest, "every Friday at 4pm, summarize unread Slack." The schedule lives in Cowork; execution is the same agent loop.

Memory: the cross-session brain

Mental model in one line. Memory is a file-based scratchpad of things Claude should remember about you across sessions. CLAUDE.md is for things about the project. Skills are for things about how to do tasks. They don't compete; they cover different territory.

What memory actually is

In Cowork, "memory" is a directory of small Markdown files plus an index file (MEMORY.md) that lists what's in there. The directory lives in your user space (not in any one project), so Claude carries it from one Cowork session to the next, and from one project to another.

Two layers, both file-based:

  1. Auto-memory. Cowork's built-in system, on by default. Files get written automatically when Claude learns something worth keeping (or when you say "remember this"). Each file is type-tagged: user (who you are), feedback (how you want to work), project (state of ongoing work), reference (where to look for things in external systems).
  2. Productivity-plugin memory. If you install the productivity plugin, you get a second tier on top: CLAUDE.md as fast working memory plus a memory/ directory for the deeper knowledge base. Opt-in. Built for people who want a more deliberate task-and-context system.

In Claude Code, the word "memory" isn't used the same way. The closest equivalents are CLAUDE.md and CLAUDE.local.md at the user or project level. If a Claude Code conversation says "save this to memory," it usually means append it to one of those files.

File structure

A typical auto-memory directory looks like this:

memory/
├── MEMORY.md                    # the index (always loaded into context)
├── user_role.md                 # who Michael is, what he does
├── feedback_no_emdashes.md      # rule: never use em-dashes
├── project_guide_watcher.md     # the daily watcher's setup and conventions
└── reference_anthropic_docs.md  # where to find Anthropic's release notes

MEMORY.md is just a list of one-line pointers, one per file:

- [User role](user_role.md). Michael is a Cowork user building reference content for himself.
- [No em-dashes](feedback_no_emdashes.md). Never use em-dash or en-dash characters.
- [Guide watcher](project_guide_watcher.md). Daily 9am scheduled task that watches Anthropic for guide-relevant news.
- [Anthropic docs locations](reference_anthropic_docs.md). Where release notes, news, and the engineering blog live.

Each individual file has YAML frontmatter and a body:

---
name: feedback_no_emdashes
description: Hard rule, never use em-dashes or en-dashes anywhere
type: feedback
---

Don't use the characters `—` (em-dash) or `–` (en-dash) anywhere.

**Why:** Michael finds them visually noisy and asked me to ban
them. They look like double hyphens.

**How to apply:** When you'd reach for one, use a period, comma,
colon, or parentheses instead. If a sentence reads awkwardly
without one, rewrite the sentence.

How memories get saved

Three triggers:

  1. You ask explicitly. "Remember that I prefer X." Claude writes it to memory immediately.
  2. Claude notices something worth saving. A correction you make ("don't do it that way"), a confirmed approach ("yes, that's exactly right"), a fact about ongoing work that won't change soon ("we use Snowflake, not BigQuery").
  3. You ask Claude to forget something. Claude finds the relevant entry and removes it.

Claude is supposed to not save:

  • Code patterns, file paths, project structure. Those live in the code; reading the code is more reliable than recalling a stale memory.
  • Debug-fix recipes. The fix is in the code; the commit message has the context.
  • Ephemeral task state. That belongs in the current conversation or a TASKS.md, not memory.
  • Sensitive personal info (medical, financial, government IDs, home address) unless you explicitly ask for it.

How memories get invoked

MEMORY.md (the index) is loaded into context every turn. So Claude always knows what memories exist, even before reading any of them.

Individual memory files are loaded on demand, when their description in the index matches something in the current conversation. Ask about your daily watcher and Claude reads project_guide_watcher.md. Don't, and that file's contents stay on disk.

Token cost

Two costs, in two places:

  • MEMORY.md loads every turn. Capped at roughly 200 lines, one-line entries each, so it costs maybe 1 to 3k tokens per turn (same neighborhood as a tight CLAUDE.md).
  • Individual memory files load only when invoked. A file you wrote three months ago and haven't touched costs zero tokens until something in the current conversation matches its index entry.

The practical consequence: don't worry about having "too many" memories, as long as the index entries are short and well-named. Worry about the index getting bloated.

Do memories need specific formatting?

Light formatting; not a free-form brain dump.

The frontmatter (name, description, type) is required. The body is prose. For feedback and project types, a strong pattern is:

[The rule or fact]

**Why:** [the reason; often a past incident or strong preference]

**How to apply:** [when this kicks in, how to behave when it does]

Including the why matters more than it sounds like. Stale memories are the worst kind; a memory you can re-evaluate ("does this reason still apply?") ages better than one you can only re-apply blindly. Future-Claude reading your memory file in three months will thank past-Claude for explaining the reason.

For user and reference types, you can be terser. A user memory might just be a few sentences. A reference memory is often a single sentence pointing somewhere external.

Practical patterns

  • "Remember I'm a designer, not an engineer." A user memory. Affects how Claude pitches every explanation thereafter.
  • "Stop adding emojis to my docs." A feedback memory with a reason. Holds across projects.
  • "The watcher runs at 9am daily and writes to proposed-updates.md." A project memory. Lets future sessions pick up where this one left off.
  • "Anthropic's release notes live at docs.claude.com/en/release-notes/claude-code." A reference memory. Saves the lookup.
Common confusions
  • "Memory is automatic, I don't have to do anything." Mostly true, but quality is much higher when you correct things proactively. If Claude saves something you'd rather it didn't, say so; if Claude misses something you wish it remembered, ask it to save it.
  • "More memories = better." Not really. Quality and naming beat quantity. The index has to stay scannable.
  • "Memory replaces CLAUDE.md." They cover different territory. Memory is about you and your patterns. CLAUDE.md is about the project. A team project still needs CLAUDE.md so teammates inherit the context; memory is yours alone.
  • "Memory persists across products." Cowork's auto-memory is per-Cowork-account. It doesn't carry into Claude Code or claude.ai. If you want Claude Code to know something durable, put it in ~/.claude/CLAUDE.md (user level).

What carries across, what doesn't

  • Carries across: the engine (loop + model), MCP, the idea of skills and plugins, hooks (where supported).
  • Cowork-only: artifacts, connectors-as-UI, scheduled tasks, workspace-folder concept, auto-memory (the cross-session brain), role-based onboarding.
  • Claude Code-only: CLAUDE.md as a first-class file in the repo, the terminal surface, IDE integrations, repo-level git workflows.

Part 11Cheat sheets and quick references

Concept one-pagers

CLAUDE.md. Project-specific system prompt. Loaded every turn. Use @path to import files. CLAUDE.local.md for machine-specific, gitignored stuff. Keep it lean.

Skill. Folder with SKILL.md. Description is the trigger. Body only loads when fired. Build company-specific, pull trusted for generic, fork when close-but-not-quite.

MCP. A process exposing tools to agents. Installs at user or project scope. All tool schemas load at session start, chatty MCPs are expensive. Treat installs like curl | bash.

Sub-agent. Isolated context window. Returns a single message to the parent. Keeps the main context clean. Not automatically faster, isolating, not accelerating.

Plugin. A bundle of any of the above. Installed from a marketplace. Anthropic official + many community ones.

Connector. Cowork's name for an MCP-backed integration to a specific service.

Mode. Permission posture. Default / Accept Edits / Plan (read-only) / Bypass / Auto (new, classifier-based).

Hook. Shell command fired at a lifecycle point. Deterministic behavior on top of the non-deterministic model.

Memory. Cowork's cross-session brain. MEMORY.md index loads every turn (cheap); individual type-tagged files (user, feedback, project, reference) load on demand. Remembers things about you, not the project.

Common confusions roll-up

  1. CLAUDE.md is a README. No, it's a system-prompt append. Different audience, different content.
  2. Plan mode means "no tools." No, read-only. It can still explore.
  3. MCPs are free until you use them. No, their schemas cost tokens at every session start.
  4. A skill is just a prompt template. No, it can include scripts and reference files, and its selection is automatic based on description matching.
  5. Sub-agents are faster than doing it yourself. Not inherently, they isolate context. Parallel Task calls are faster.
  6. "Agent" has one meaning. No, at least four (Task tool, named sub-agent, parallel Tasks, separate sessions).
  7. The Agent SDK is a separate product from Claude Code. They share the underlying loop; the SDK was extracted from Claude Code.
  8. 60% / 80% context thresholds are official. They're heuristics. Anthropic doesn't publish these.
  9. The terminal is the only Claude Code. No, but it's historically the most feature-complete surface. Verify for your version.
  10. Antigravity is Google's. Yes, the product name is Antigravity.
